The problem

Sending every message to a big LLM is wasteful

"I forgot my password"

Needs a reset link. A script can do that.

Sending it to an LLM costs money and seconds.

"Why does SSO fail after the token expires?"

Open-ended. Needs real reasoning.

This one should go to the LLM.

Say: Most requests are routine. The trick is telling the routine ones apart quickly and cheaply.
The idea

Put a small decision model in front

Steps 1 and 2 are the decision model. It never writes text. It picks from fixed options and returns a confidence score.

Say: The small model decides. Code acts. The LLM only shows up for the hard stuff.

The rules

What happens with each message

Step 1: Safety

Attack score ≥ 0.80 → BLOCK

Runs before anything else. Nothing downstream sees the message.

Step 2: Confidence

ACT ≥ 0.85

ASK 0.50 to 0.85 ("did you mean...?")

ESCALATE below 0.50

Three buckets: reset_password · unlock_account · llm_reasoning

Say: Same rules for both models. The only thing that changes is who makes the call.

How to read it

Five things on screen

choiceWhich bucket the model picked
confidenceHow sure it is (0 to 1). Drives act / ask / escalate
pathWhat actually ran: code, LLM, block, or escalate
latencyTime spent deciding
STATSdecided_without_llm: messages the LLM never saw
Say: The number to watch is decided_without_llm. That's money and time you didn't spend.
Takeaways

What to take home

  • Decision models pick from options and tell you how sure they are
  • Put one in front of your LLM: routine work goes to code
  • Use confidence to decide: act, ask, or escalate
  • Hosted (Jev) or local and open (Strands Decider): pick for your constraints
